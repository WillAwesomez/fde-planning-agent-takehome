## What I deliberately did not do, and why

In `agent._execute_tool_step` (shipped code), only `web_search` results get merged
into `run.sources` -- the branch that inspects a tool's JSON result and appends
URLs checks `if name == "web_search"` and has no matching case for `fetch_url`,
even though `fetch_url` echoes back the exact `url` it read in its own JSON
(`{"url": ..., "text": ...}`). So a step that reads one page in full via
`fetch_url` never gets that page credited as a source in the final answer or the
UI's Sources list, which undercuts the "cite what you actually read" story for
exactly the tool that reads the most. I left it alone because it lives inside
`execute_step`, which the brief marks as provided/not-mine-to-touch, and because
I couldn't rule out a hidden grading test pinning today's `sources` behavior
exactly. I'd fix it (one line, mirroring the `web_search` branch) the moment
someone confirms citation completeness for `fetch_url` steps actually matters to
the ops team, or a test says otherwise.

Separately, in `revise_plan` I chose to treat a syntactically valid but *empty*
`{"steps": []}` reply the same as a garbage reply -- both fall back to returning
`remaining` unchanged rather than trusting the model's "nothing left to do."
`REVISER_SYSTEM` never actually licenses an empty list (the last step must
always be `"none"`), so a truly empty parse is indistinguishable from a
malformed one, and silently ending the run early is worse than keeping the
steps the user already approved. I'd revisit this if the prompt were changed to
make an intentional empty list a valid, distinguishable response.

## How I would know this works

Because live mode is non-deterministic by construction, the repeatable read has
to come from the offline side: I'd run a fixed set of ~20-30 representative
goals through `run_planning_agent` in `LLM_MODE=replay` on every change and diff
`stopped_reason`, step count, revision count and final-answer shape against the
last known-good snapshot -- since replay is deterministic, any difference here
is a code regression, not model drift, and that diff should be exactly zero.
Against live traffic I'd track a handful of rates over rolling windows: the
share of runs ending `stopped_reason == "error"` (excluding user cancellations),
the share of `write_plan`/`revise_plan` calls that hit the JSON-parse fallback
(both currently swallow malformed model output silently, so without this metric
a spike in bad model output is invisible), and the share of steps whose
observation starts with `"surprise"`. A rough bar: error rate above 2-3% or a
parse-fallback rate above 5% both mean the model is drifting off the expected
JSON contract and someone should look; a surprise rate that drops to near zero
is just as suspicious as one that spikes, since it likely means the observer
itself broke rather than that every run is going smoothly. I'd also watch P95
run latency and the fraction of tool-heavy runs that end with an empty
`sources` list, since both degrade silently -- the user still gets an answer,
just a slower or less-grounded one, with nothing in `stopped_reason` to flag it.
